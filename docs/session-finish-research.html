1 What actually happens when a session finishes

Two entry points, both in the extension service worker — and there is no “Complete now” button. The popup only has Stop, which is a cancel (completed=false).

  • Natural completion — a SESSION_END_ALARM scheduled at start (service-worker.ts:127) fires → handleSessionEnd (service-worker.ts:178).
  • User stop — Stop sends focusquote.session.cancel (SessionPanel.tsx:108) → handleSessionCancel.

Extension side — handleSessionEnd

  1. Local write firstsessions.complete(id, true) rewrites the local session record (completed=true + endedAt), removes the activeSession key, and enqueues an upsertSession sync job (sessions.ts:32).
  2. Push to serverSyncService.drain() posts the queue to POST /api/sync/batch. Auth-gated — for signed-out users this is a silent no-op and the row never reaches the server.
  3. URL flush (no-op)UrlTracker.flush() — webNavigation URL capture is currently commented out (service-worker.ts:573-588), so the buffer is normally empty.
  4. Cleanup & notifyClears alarms / badge, fires a Chrome notification, broadcasts focusquote.session.finished. No LLM call happens on the extension side.

Server side — a side-effect of the batch upsert

Completion logic lives in sync.ts:75-87 (the real path), not the dedicated focus-sessions.ts handler. When a batched job is completed=true, it fires — all fire-and-forget / un-awaited:

  • maybeGenerateSummary, maybeGenerateStudyTips, maybeGenerateRecallQuestions, maybeGenerateResourceRecommendations
  • maybeGenerateTopic(...).then(() => flushPendingSessionVault(...)) — Haiku classifies the session into 1 of 12 fixed categories, then promotes pending vault items into the resolved topic (or “Uncategorized”)
  • maybeGenerateTitle
  • Separately sweeps pending quotes into the Tag graph
⚠ Two completion paths have diverged

The focus-sessions.ts downstream() block (185-208) — which awaits topic before flush, gates auto-title vs. auto-goal, and calls maybeAutoDeriveGoal — sits behind POST /api/focus-sessions, whose client method has zero call sites. The extension only ever hits sync.ts. So that careful sequencing is effectively dead code, and maybeAutoDeriveGoal never runs on the real finish flow.

UI reaction is passive: the newtab toasts + refreshes Home (App.tsx:204); it does not navigate to the report. The full report (SessionDetail.tsx) is user-initiated and lazy — its GETs re-fire generation when completed && artifact missing, so clicking in immediately may show empty panels until background work lands.

2 Is vault data being used?

Write-mostly-dead Vault items are written from 4 surfaces, read for display in exactly 1, and feed zero LLM prompts. Verified by grep over llm.ts, study-artifacts.ts, summary.ts, topic.ts, tags.ts — none reference topicVaultItems / sessionVaultItems.
AspectVault items
Written fromtoolbar bookmark (/focus-sessions/:id/vault-link), annotate “Save to Vault” & right-click image (/vault/save), newtab manual add (/topics/:id/vault)
Read for displayone surface only — GET /topics/:id/vault → newtab Topics-tab per-topic panel (TopicsSection.tsx)
Fed into any promptnever
Dead read pathGET /focus-sessions/:id/vault-pending + clients listSessionVaultPending / attachSessionVaultLink / assignSessionTopic have zero call sites

flushPendingSessionVault is called on completion, but it’s pure data movement (promote pending → topic) — it organizes items, it doesn’t surface them anywhere new.

The same is true of screenshots — the actual broken promise

topic_media (screenshots) is also fed to zero prompts, despite the schema comment at schema.ts:571-573 claiming it’s “Used to enrich the LLM prompts for recall + resource recommendations” and the UI copy at TopicsSection.tsx:715 echoing it. In lib code topicMedia appears only inside a backfill migration — never in a prompt builder.

So the two richest signals of user intent — what they bookmarked and what they screenshotted — inform none of the AI features, while the one input that is used (session_urls) is usually empty because URL capture is disabled.

3 The real relation between quotes, topics, sessions & vault

The system is two disconnected universes, joined at nothing.

Universe A

Sessions · Topics · Vault — well-connected by FKs

  • focus_sessions.topicId → topics.id
  • topic_vault_items.topicId → topics.id
  • session_vault_items.sessionId → focus_sessions.id
  • session_urls / session_actions → focus_sessions.id
  • topic_media.topicId → topics.id (half-migrated)
NO LINK

Universe B

Quotes · Tags — separate by ADR-0003 design

  • quote_tags → quotes + tags
  • tag_edges form a DAG over tags
  • server-side Haiku files quotes into the taxonomy
  • no quotes.topicId
  • no quotes.sessionId
RelationshipFK?Notes
focus_sessions → topicsEXISTSThe grouping key. Sessions the AI labels “Programming” repoint at the same topics row via a (userId, name) unique index. A legacy free-text focus_sessions.topic string is kept in sync alongside the FK — dual source of truth.
topic_vault_items → topicsEXISTSNOT NULL. The durable curated vault, keyed by topic.
session_vault_items → focus_sessionsEXISTSPre-topic staging; no topicId column. Promoted to topic_vault_items at completion.

quote_tags → quotes + tagsEXISTSMany-to-many; tags form a DAG. A user-global taxonomy, independent of sessions/topics by design.

quotes → focus_sessionsDOES NOT EXISTQuotesService.save ignores the active session entirely.
Consequence

The product literally cannot answer “which quotes did I save during this focus session / under this topic.” Two AI taxonomies — a tag DAG over quotes and a topic graph over sessions — evolve in total isolation with no cross-pollination. (Aside: the newtab “DailyQuote” is misnamed — it re-rolls a random quote on every page load, no per-day seed.)

4 What could be improved — ranked by leverage

#1
Effort · MImpact · High

Feed vault items + screenshots into the recall / resources / summary prompts

The deliberate-curation signal drives none of the AI. Load the resolved topic’s topic_vault_items (+ pending session_vault_items, + topic_media captions, and the image bytes — the model is multimodal) into the prompt builders.

Proposal: extend study-artifacts.ts / summary.ts load steps to include a “savedByUser” block, gated by the existing AI feature switches. Especially valuable because URL capture is off, so the vault is often the only real content. Fulfills the promise the schema/UI already make.

#2
Effort · MImpact · High

Stamp quotes with the active session’s topic at capture

Quotes are a parallel universe — no sessionId, no topicId; QuotesService.save ignores the active session.

Proposal: read activeSession in QuotesService.save and persist a nullable sessionId/topicId on the quote (backwards-compatible nullable migration). Then surface “quotes saved during this session” in the report, and pass the topic name as a hint into the Haiku quote classifier. Bridges the two universes without violating ADR-0003.

#3
Effort · MImpact · Med

Consolidate the two diverged completion blocks

sync.ts:75-87 and focus-sessions.ts:185-208 have drifted; only the latter derives a goal and awaits topic-before-flush, but the extension never hits it — so maybeAutoDeriveGoal is dead and a fix to one path misses the other.

Proposal: extract one runCompletionDownstream(userId, sessionId) called from both endpoints. Also a precondition for #1 landing on the path users actually hit.

#4
Effort · SImpact · Med

Fix a latent data-loss bug in promoteSessionVaultItems

vault.ts:269-309 does onConflictDoNothing on the stable id, then unconditionally deletes all pending rows. If an item was flushed to “Uncategorized” and the session later resolves a real topic, the re-promotion is silently dropped and the source destroyed.

Proposal: upsert the topicId on conflict, or use .returning() and delete only the ids actually inserted.

#5
Effort · SImpact · Med

Decide on URL distraction classification

classifyBatch is commented out (session-urls.ts:85), so category/distractionScore are always null — yet category is still injected into every prompt as a dead field.

Proposal: either re-enable it behind the AI gate (using the url_classifications hostname cache), or strip category from the prompt builders.

#6
Effort · SImpact · Low

Smaller wins

Include topic/topicId in toSessionDTO (currently omitted, so the client can’t show a session’s topic) · add a “View report” action to the finish toast + a generating state in SessionDetail · add a real “Finish as completed” button (today early-finish can only cancel, which never feeds the streak) · add an onConflict upsert to ensureTopicId (concurrent completions into a new category can throw on the unique index).

5 Latent bugs surfaced along the way

Data loss

promoteSessionVaultItems (vault.ts:269-309) — onConflictDoNothing + unconditional delete can drop re-promotion to a corrected topic and destroy the source row. (See improvement #4.)

Race condition

ensureTopicId (topic.ts:191-205) is a SELECT-then-INSERT with no onConflict. Two sessions completing concurrently into the same new category can both miss the existing row and the second INSERT throws on the (userId, name) unique index.

Re-trigger

maybeGenerateTopic gates on session.topic (legacy string) not topicId (topic.ts:152), so a row with topicId set but topic null could re-run the AI classification.

Silent drop on redeploy

All completion AI work is fire-and-forget (void downstream()). Lazy-regen on GET covers summary/tips/recall/resources, but topic/title/goal have no safety net — a redeploy mid-run silently drops them.

The structural theme: FocusQuote captures a lot of intentional user signal (bookmarks, annotations, screenshots, quotes) and stores it carefully, but the AI features consume almost none of it — they run off session_urls, which is currently empty. Wiring curation back into the prompts (#1) and bridging quotes to sessions (#2) is where the product gets its compounding value.
